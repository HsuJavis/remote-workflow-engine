# S2 — if arm 1 is inert, does the same object via `Options.settings = { sandbox: {...} }` confine? (arm 2)

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

## Preliminary static finding (read from the installed `sdk.mjs`, not documentation)
`node_modules/@anthropic-ai/claude-agent-sdk/sdk.mjs` contains function `aI(e,t)` (the `Options`→CLI-args
assembler's sandbox handling): when `options.sandbox` (arm 1) is set, it does **not** emit a separate
`--sandbox` CLI flag — it merges `{sandbox: <your object>}` into whatever `options.settings` already is
and emits that as the single `--settings <json>` CLI argument (the flag-settings layer). **Arm 1 and arm
2 are therefore the same wire representation in this SDK version**, not two independent code paths.

constructs directly: `{"sandbox":{"enabled":true,...,"filesystem":{...}}}`.)

## Verdict
- **verdict:** Arm 2 (`Options.settings.sandbox`) is empirically byte-equivalent to arm 1 (`Options.sandbox`) on this SDK version — confirmed by matching real-run behavior, not just static reading.

**Arm 2 is empirically equivalent to arm 1 on this SDK version — confirmed both statically (same merge
function `aI()`) and by running it and getting byte-identical behavior.** Since arm 1 is not inert (S1:
it drives real kernel-level sandbox setup, just blocked by a host policy issue past that point), arm 2
was never needed as a distinct fallback and the carrier ladder's arm-1/arm-2 stability claim in ADR-082
("the builder's output is identical under arms 1 and 2") holds. No further arm-2-specific testing
performed — it would exercise the identical code path already covered.
