# S9 — does one real SDLC-shaped workflow still COMPLETE under the confinement? EACCES inventory + bwrap per-call latency

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

## Whether a real workflow can complete under `sandbox.enabled:true` on this host
Every real-execution attempt in S1/S4/S5/S7/S8 (five independent probes, different prompts, different
`filesystem`/`credentials` configurations, all with `socat` reachable via PATH so the sandbox gets past
its dependency preflight) hit the **identical** failure at the **first** Bash tool call:
```
apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted;
  caller must provide CAP_SYS_ADMIN): Permission denied
```
This fires before the user's actual shell command starts (it is the sandbox's own construction step),
so it is **prompt-independent** — a longer, multi-step SDLC-shaped workflow (many Bash calls) would fail
on its very first Bash call exactly the same way a single `echo` does. Running a longer scripted
workflow end-to-end would not produce new information; the blocking point is structural, not something
that appears only under sustained load or many turns.

## Command — confirming the first-call failure is deterministic and immediate (not a race/flake)
```
for i in 1 2 3; do PATH=<scratch>/socat-extract/usr/bin:$PATH WS=<scratch>/ws1 \
  node --input-type=module -e '<S1-shaped probe>' ; done
```
### Raw output (representative; identical across S1/S4/S5/S7/S8's 5 separate real runs on this host)
```
Exit code 1
apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied
```

## EACCES inventory
**None observed.** The failure mode on this host is not a kernel `EACCES` on a specific path (which is
what ARCH-175/DES-252 and the DoD's "EACCES inventory" phrasing anticipate for `$TMPDIR`,
`~/.npm/_logs`, `~/.cache`, `~/.config/git`, compiler scratch, etc.) — it is a hard failure of the
sandbox's own construction, before any filesystem access inside the jail is attempted at all. There is
therefore **no EACCES inventory to report from this host**; the design input DES-252/DES-257 wanted
(which engine-internal directories get denied and need an explicit grant) could not be produced here.

## `bwrap` per-call setup latency
Measured directly on the layer that DOES succeed on this host (bare `bwrap --unshare-user
--unshare-pid --ro-bind / / --tmpfs /tmp -- /bin/true`, 5 runs):
```
0.00s 0.01s 0.00s 0.00s 0.00s
```
### Command
```
for i in 1 2 3 4 5; do /usr/bin/time -f "%e" bwrap --unshare-user --unshare-pid --ro-bind / / --tmpfs /tmp -- /bin/true; done
```
**~0–10ms per bwrap namespace+mount setup on this host.** Caveat: this measures only the portion of the
sandbox construction that succeeds here (namespace creation + bind mounts) — it excludes the
`apply-seccomp` step and the socat-based network bridge (`Tla()` in the bundled binary spawns two
`socat` child processes for an HTTP+SOCKS bridge when `network` restrictions are configured), neither of
which could be timed end-to-end because the sandbox never reaches a completed state on this host.

## Verdict
- **verdict:** No — a real SDLC-shaped workflow does not complete under `sandbox.enabled:true` on this host (every Bash call fails deterministically at sandbox construction, root-caused to `/etc/apparmor.d/bwrap-userns-restrict`); no EACCES inventory could be produced; bare bwrap setup itself is cheap (~0–10ms/call).

**NO — a real SDLC-shaped workflow does NOT complete under `sandbox.enabled:true` on this host as
currently provisioned.** Every Bash call fails deterministically at sandbox construction
(`apply-seccomp`/`CAP_SYS_ADMIN`, root-caused in S1 to `/etc/apparmor.d/bwrap-userns-restrict`), not at
a specific path decision. No EACCES inventory could be produced. Bare `bwrap` namespace setup itself is
cheap (~0–10ms/call) and not the bottleneck. **This is the single most consequential finding of the
whole spike**: shipping ADR-083's `failIfUnavailable:true` unconditionally on a host provisioned like
this one would make every agent run refuse to start the moment `sandbox.enabled:true` ships, unless the
host's AppArmor policy is fixed by an operator with root, or `failIfUnavailable:false` is used (which
defeats REQ-218's intent, per ADR-083's own reasoning). ADR-083's revisit trigger ("spike S6 reports that
the remote host cannot provide bubblewrap") is worded around bubblewrap *presence*, but this host
demonstrates the equivalent-in-effect failure mode with bubblewrap *present*: **"cannot provide a
working sandbox" needs to be read as including this apply-seccomp/AppArmor case**, and that reading is
recorded here as a residual for the ADR owner rather than silently assumed.
