# S7 — does a narrower `allowRead` override a broader `denyRead`? (run WITH `allowRead` set)

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

## What was run (real, with `socat` on PATH via S1's user-space workaround so the sandbox actually
## starts, not just the dependency preflight)
`filesystem = { allowWrite:[ws], allowRead:[ws], denyRead:[ws] }` — `ws` set as BOTH the allow and the
deny region (the narrowest possible test of allow-over-deny precedence for the exact same path), a real
file `ws/sub/readme_s7.txt` created beforehand, prompt asks the agent to `cat` it via Bash.

## Command
```
PATH=<scratch>/socat-extract/usr/bin:$PATH WS=<scratch>/ws1 DENY_REGION=<scratch>/ws1 \
DEBUG_CLAUDE_AGENT_SDK=1 node --input-type=module -e '<probe: query() with
  options.sandbox.filesystem = { allowWrite:[ws], allowRead:[ws], denyRead:[ws] },
  prompt "cat <ws>/sub/readme_s7.txt" via Bash>'
```

## Raw output
```
TOOL_RESULT "Exit code 1\napply-seccomp: write /proc/self/setgroups (nested userns is
  capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied"
RESULT_SUBTYPE success is_error false
```
The sandboxed `Bash` `cat` never ran — identical S1 blocker (`apply-seccomp`/`CAP_SYS_ADMIN`) fires
before the shell starts, regardless of what `allowRead`/`denyRead` were configured to. (The model then
independently used its own `Read` tool — a separate, PreToolUse-hook-governed code path, not the OS
sandbox — to answer the prompt anyway; that is unrelated to what this arm measures and is not counted
as a result.) No Bash command, confined or not, reaches the point where a kernel-enforced
`allowRead`/`denyRead` decision would actually be applied.

## What COULD be verified directly (a real file on this host, not an assumption)
```
grep -n "Takes precedence over denyRead" node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts
```
### Raw output
```
5863:             * Paths to re-allow reading within denyRead regions. Takes precedence over denyRead for matching paths.
```
This confirms the doc-comment ARCH-175/DES-252 cite is real, present in the installed package (not
invented, not stale), and states the schema's own claimed precedence rule. It is the SDK/CLI vendor's
documentation of intended behavior, not a runtime observation of this host actually applying it.

## Verdict
- **verdict:** Could not measure (same S1 blocker); the `allowRead`-precedence doc comment is confirmed real/current text in the installed SDK, but its runtime enforcement was not observed — `DENY_READ_MODE` must stay `'enumerated'`, not flip to `'workroot'`, on this evidence.

**COULD NOT MEASURE — same S1 blocker (no Bash command completes under an active sandbox on this
host).** The doc-comment asserting `allowRead` takes precedence over `denyRead` is confirmed to be
real, current text in the installed `sdk.d.ts` (not fabricated), but its *enforcement* was not
observed. Per DES-252's own fallback: `DENY_READ_MODE` should ship as **`'enumerated'`** (the built-in,
safer posture) until a positive S7 is obtained elsewhere (e.g. a host without this AppArmor restriction,
or after this host's policy is fixed by an operator with root) — the `'workroot'` arm must NOT be
adopted on the strength of the doc comment alone, exactly as DES-252 anticipates for a non-run spike arm.
This is an honest "could not measure", not a guessed yes.
