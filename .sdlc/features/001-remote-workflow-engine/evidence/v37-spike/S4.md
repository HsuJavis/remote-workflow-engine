# S4 — does `PostToolUseFailure` fire for a sandbox-denied command?

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

## Command — real `query()` call with `hooks.PostToolUseFailure` and `hooks.PostToolUse` both registered,
## `options.sandbox` enabled with `socat` reachable via PATH (S1's workaround) so the sandbox actually
## starts and the Bash tool call fails inside it (apply-seccomp/CAP_SYS_ADMIN, per S1) rather than
## failing at the dependency preflight
```
PATH=<scratch>/socat-extract/usr/bin:$PATH WS=<scratch>/ws1 TARGET=/tmp/OUTSIDE_SANDBOX_TEST_s4.txt \
DEBUG_CLAUDE_AGENT_SDK=1 node --input-type=module -e '<probe: query() with
  options.sandbox = {...same as S1...},
  options.hooks.PostToolUseFailure = [{hooks:[async (input) => { hookFired.push(input) }]}],
  prompt "echo hacked > $TARGET; cat $TARGET; echo EXIT:$?" via Bash>'
```

## Raw output
```
RESULT_SUBTYPE success is_error false
HOOK_FIRED_COUNT 1
HOOK_FIRED_JSON [{
  "session_id": "40024dab-1143-4344-b4c1-817c2b59d010",
  "hook_event_name": "PostToolUseFailure",
  "tool_name": "Bash",
  "tool_input": {
    "command": "echo hacked > /tmp/OUTSIDE_SANDBOX_TEST_s4.txt; cat /tmp/OUTSIDE_SANDBOX_TEST_s4.txt 2>&1; echo EXIT:$?",
    "description": "Attempt to write and read a file in /tmp"
  },
  "tool_use_id": "toolu_01CY3u82jjrytyLJb5LDHsXe",
  "error": "Exit code 1\napply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied",
  "is_interrupt": false,

```
`PostToolUseFailure` fired exactly once, carrying `tool_name:"Bash"`, the full `tool_input.command`, and
an `error` string containing the sandbox layer's own raw stderr text. The registered `PostToolUse`
(success-only) hook did **not** fire for this call (consistent with the SDK's own `HOOK_EVENTS` split).

## Caveat, stated precisely
The failure observed here originates from the sandbox's own **initialization** step (`apply-seccomp`
failing to set up its nested-userns seccomp filter — see S1), not from a clean **path-denial** (e.g. a
kernel `EACCES` on a write outside `allowWrite`) — a true path-denial could not be produced on this host
because no Bash command can complete under an active sandbox here at all (S1). However, hook *firing* is
gated on the tool call's exit/error state, not on which layer produced the error — the CLI does not
distinguish "sandbox init failed" from "sandbox denied this specific path" when deciding whether to
invoke `PostToolUseFailure`. This is real, positive evidence that the hook fires for sandbox-caused Bash
failures in general, which is what ARCH-178/DES-256 condition `agent.confinement_denied`'s existence on.

## Verdict
- **verdict:** Positive — `PostToolUseFailure` fires for a sandbox-caused Bash failure, carrying `tool_name`, `tool_input.command` and a raw `error` string; `agent.confinement_denied` should be built.

**POSITIVE — `PostToolUseFailure` fires for a sandbox-caused Bash tool failure, carrying `tool_name`,
`tool_input.command`, and a raw `error` string.** `agent.confinement_denied` (ARCH-178, DES-256) should
be built. Not independently confirmed for the narrower "clean EACCES path-denial" sub-case (blocked by
S1's host issue), but no mechanism in the CLI distinguishes that sub-case from what was measured, so the
positive result is expected to generalize; this is named as the residual, not silently assumed.
