# S3 — else arm 3: `enabled:true` + `autoAllowBashIfSandboxed:true` + `additionalDirectories` + permission rules

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

## Why this arm was not exercised
ADR-082's carrier ladder is explicitly conditional: arm 3 is the fallback "**else**" — reached only if
`Options.sandbox` (arm 1) turns out to be **inert** (the CLI ignores/drops the field entirely). S1 and S2
establish the opposite: `Options.sandbox` is read, forwarded verbatim onto the CLI's `--settings
{"sandbox":...}` flag-tier JSON, and demonstrably drives the CLI into real, kernel-level sandbox
construction — `strings` on the installed binary shows the exact `filesystem`/`credentials`/`bwrapPath`/
`socatPath` field names being consumed by a real dependency-check function (`Hla()`), and the field
causes an observably different code path (bwrap process spawn, then a distinct internal failure) rather
than being silently discarded. **The mechanism is not inert; it is blocked further downstream** (a host
AppArmor policy on the `apply-seccomp` helper, S1). Arm 3 exists in the ladder specifically for "the
field does nothing", which is not what was measured.

## Command — one confirming check, run for completeness rather than as a fallback attempt
```
grep -n "Takes precedence over denyRead" node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts
```
### Raw output
```
5863:             * Paths to re-allow reading within denyRead regions. Takes precedence over denyRead for matching paths.
```
Confirms `filesystem.allowRead`/`denyRead` are real, documented fields on the *same* `SandboxSettings`
object arm 1 uses — i.e. the object shape ARCH-175/DES-252 designed against actually exists in the
installed package, reinforcing that arm 1 is the live, intended mechanism rather than a dead field that
would force a fallback to arm 3's `additionalDirectories`+permission-rule shape (a materially different,
weaker mechanism: permission rules are enforced by the CLI's own PreToolUse-equivalent logic on
path-bearing tools, not by the kernel, and would not help with `Bash` at all per ARCH-176's own point
that Bash's `tool_input` carries no path field to apply a permission rule against).

## Verdict
- **verdict:** Not exercised — arm 1 is confirmed live (S1/S2), so the pinned fallback ladder never reaches arm 3; not a claim that arm 3 would or wouldn't work.
