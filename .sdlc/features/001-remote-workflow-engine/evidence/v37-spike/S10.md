# S10 — is `failIfUnavailable:true`'s failure distinguishable from an ordinary terminal failure?

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199`

This host genuinely cannot provide a working sandbox (S1/S9: dependency preflight fails without a
user-space `socat`, and even with `socat` supplied the `apply-seccomp` step fails on the host's AppArmor
policy) — i.e. it IS "a host where the sandbox cannot start", exactly the precondition this arm asks
about, obtained for free rather than simulated.

## Command 1 — capture the exact result shape for the sandbox-unavailable failure
```
WS=<scratch>/ws1 node --input-type=module -e '<probe: query() with options.sandbox.enabled=true,
  failIfUnavailable=true, socat NOT on PATH, prompt "echo hacked > $TARGET" via Bash;
  print every yielded message as full JSON, and the message of any thrown error>'
```
### Raw output
```
MSG_FULL {"type":"result","subtype":"error_during_execution","duration_ms":0,"duration_api_ms":0,
 "is_error":true,"num_turns":0,"stop_reason":null,"session_id":"50e06c0b-...","total_cost_usd":0,
 "usage":{...all zero...},"permission_denials":[],"uuid":"33d69b11-...",
 "errors":["Sandbox required but unavailable: sandbox is enabled but dependencies are missing:
   socat not installed · install missing tools (e.g. apt install bubblewrap socat) or see
   https://code.claude.com/docs/en/sandboxing. Set sandbox.failIfUnavailable=false to allow
   unsandboxed execution."]}
LOOP continues, then query() THROWS on the next iteration:
THROWN_ERROR_NAME Error
THROWN_ERROR_MESSAGE Claude Code returned an error result: Sandbox required but unavailable: sandbox is
  enabled but dependencies are missing: socat not installed · install missing tools (e.g. apt install
  bubblewrap socat) or see https://code.claude.com/docs/en/sandboxing. Set sandbox.failIfUnavailable=
  false to allow unsandboxed execution.
```
Key shape facts: `subtype:"error_during_execution"`, `num_turns:0` (the agent never got to act at all),
the message text lives in an **`errors` array field**, not the usual `result` string, and `query()`'s
async iterator subsequently **throws** an `Error` whose `.message` is
`"Claude Code returned an error result: " + <the errors[0] text>` — i.e. the gateway's `catch` around
`invoke()` sees this as a thrown exception, not as a value on a yielded message, and must read
`e.message` to get the detail text.

## Command 2 — contrastive "ordinary terminal failure" (an unrelated real failure: an invalid model name)
```
WS=<scratch>/ws1 node --input-type=module -e '<same probe shape, no sandbox option,
  options.model = "definitely-not-a-real-model-xyz", prompt "say hi">'
```
### Raw output
```
MSG_FULL {"type":"result","subtype":"success","is_error":true,"api_error_status":404,
 "duration_ms":845,"num_turns":1,
 "result":"There's an issue with the selected model (definitely-not-a-real-model-xyz). It may not
   exist or you may not have access to it. Run --model to pick a different model.", ...}
THROWN_ERROR_MESSAGE Claude Code returned an error result: There's an issue with the selected model
  (definitely-not-a-real-model-xyz). It may not exist or you may not have access to it. ...
```

## Comparison — structurally different, not just textually different
| | sandbox-unavailable | ordinary terminal failure (bad model) |
|---|---|---|
| `subtype` | `"error_during_execution"` | `"success"` (despite `is_error:true`) |
| detail field | `errors: [string]` (array) | `result: string` |
| `api_error_status` | absent | `404` |
| `num_turns` | `0` (never started) | `1` (a turn happened) |
| thrown message prefix | `"Sandbox required but unavailable: "` | `"There's an issue with the selected model"` |

## Verdict
- **verdict:** Yes, distinguishable — `subtype:"error_during_execution"` + `errors` array + `num_turns:0`, and the literal prefix "Sandbox required but unavailable: ", both differ from an ordinary terminal failure's shape (`subtype:"success"` + `result` string + `api_error_status`).

**YES — distinguishable, on two independent axes.** (1) The message shape itself differs:
`subtype:"error_during_execution"` + an `errors` array + `num_turns:0`, vs. the ordinary case's
`subtype:"success"` + a `result` string + a nonzero `num_turns`/an `api_error_status`. (2) The literal
text `"Sandbox required but unavailable: "` is a stable, greppable prefix distinct from any other error
text observed. DES-259's mapping is directly actionable: `enrich()`/the gateway's catch handler can test
`e.message.includes('Sandbox required but unavailable')` (or the `subtype === 'error_during_execution'`
+ `errors[0]` shape, whichever the gateway's existing error-handling code already keys off of) to set
`detail = \`${SANDBOX_UNAVAILABLE}: ${e.message}\`` reliably. ADR-083's revisit trigger ("an operator
reports a run refused for `sandbox unavailable`") is satisfiable from the log with this mapping in place.
