# S1 — does `Options.sandbox.filesystem.allowWrite` actually confine a Bash write? (arm 1)

- **date:** 2026-09-22
- **host:** javis / Linux 7.0.0-22-generic x86_64, node v22.22.3, `@anthropic-ai/claude-agent-sdk@0.3.199` (spawns bundled `claude` 2.1.199 — see S6)

## Command — real `query()` call, `options.sandbox` set, workspace-only `allowWrite`, prompt asks the agent to write outside it
```
ARM=1 WS=<scratch>/ws1 TARGET=/tmp/OUTSIDE_SANDBOX_TEST_s1.txt DEBUG_CLAUDE_AGENT_SDK=1 \
node --input-type=module -e '<probe: query() with
  options.sandbox = { enabled:true, failIfUnavailable:true, autoAllowBashIfSandboxed:true,
    allowUnsandboxedCommands:false,
    filesystem:{ allowWrite:[ws], allowRead:[ws], denyRead:[], denyWrite:[] } },
  prompt "echo hacked > $TARGET; cat $TARGET; echo EXIT:$?" via Bash>'
```

## Raw output — attempt 1 (no extra dependencies installed)
```
RESULT_SUBTYPE error_during_execution is_error true
ERR Claude Code returned an error result: Sandbox required but unavailable: sandbox is enabled but
dependencies are missing: socat not installed · install missing tools (e.g. apt install bubblewrap socat)
or see https://code.claude.com/docs/en/sandboxing. Set sandbox.failIfUnavailable=false to allow
unsandboxed execution.
FILE_EXISTS_ON_DISK false
```
Fails closed correctly (no write reached disk) — but this only proves the *dependency preflight*, not confinement of an actual command.

## Obtaining `socat` without root (apt-get download + dpkg-deb -x, no sudo), retry
```
cd /tmp && apt-get download socat          # succeeds, no root needed, downloads .deb to cwd
dpkg-deb -x socat_1.8.1.1-1ubuntu0.1_amd64.deb <scratch>/socat-extract   # extracts, no root needed
PATH="<scratch>/socat-extract/usr/bin:$PATH" <same probe as above>
```
### Raw output — attempt 2 (socat on PATH)
```
RESULT_SUBTYPE success is_error false
result: "apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted;
  caller must provide CAP_SYS_ADMIN): Permission denied"  (Exit code 1)
FILE_EXISTS_ON_DISK false
```
`bwrap` dependency + `socat` dependency now both satisfied; the CLI proceeds past the preflight and
actually starts building the sandboxed process — **but the target `echo`/`cat` command never runs at
all**: a CLI-internal helper (`apply-seccomp`, installs a seccomp-bpf filter that blocks raw AF_UNIX
socket creation inside the sandbox — found via `strings` on the bundled binary at
`node_modules/@anthropic-ai/claude-agent-sdk-linux-x64/claude`, literal `apply-seccomp binary`,
`function Hla(){...bwrapPath...socatPath...}`) itself needs to create a **second, nested** unprivileged
user namespace, and that is denied.

## Root-caused (real files on this host, not guessed)
```
cat /etc/apparmor.d/bwrap-userns-restrict
```
Ubuntu's default AppArmor profile scoped to `/usr/bin/bwrap`: it stacks a child profile
(`unpriv_bwrap`) onto anything `bwrap` execs inside the namespace it creates, and that child profile
contains `audit deny capability` — i.e. **every process bwrap spawns inside its own sandbox has ALL
Linux capabilities stripped by host policy**, including the `CAP_SYS_ADMIN` `apply-seccomp` needs for
its own (second-level) `unshare(CLONE_NEWUSER)`. A bare, unwrapped `bwrap --unshare-user ... /bin/echo`
(no nested apply-seccomp step) succeeds fine (`EXIT:0`) — confirming the block is specific to the
nested-namespace step inside bwrap's own sandbox, not bwrap itself.

## Workaround attempted and failed
Passed `sandbox.seccomp.applyPath` pointing at a no-op shim (`#!/bin/sh; exec "$@"`) — the CLI still
invoked the real bundled `apply-seccomp` and produced the identical error, i.e. the override was not
honored via the public `Options.sandbox` surface on this SDK/CLI version pair. No root-free path around
this was found.

## Verdict
- **verdict:** Inconclusive on this host — `Options.sandbox` is not inert (drives real bwrap construction) but no Bash command completes under it here (blocked by a host AppArmor policy on `apply-seccomp`, not by the SDK wiring).

**INCONCLUSIVE ON THIS HOST for the write-confinement question itself** — `Options.sandbox` is not
inert (it is read, forwarded verbatim as the CLI's `--settings {"sandbox":...}` flag-tier JSON — see
S2, and it drives the CLI into real kernel-level sandbox setup, confirmed by `strings` on the actual
enforcement code and by the `PostToolUseFailure` hook firing with the sandbox-layer error text, S4) —
but **no Bash command can complete under `sandbox.enabled:true` on this host at all**: every attempt
fails at the `apply-seccomp` nested-userns step before the user's shell command starts, root-caused to
the host's `/etc/apparmor.d/bwrap-userns-restrict` capability-stripping policy. Confining a permitted
vs. denied write could not be directly observed; fixing this needs root (either install `socat`
system-wide is not the blocker — the AppArmor policy is — a local policy exception or running as a user
whose `bwrap` children retain `CAP_SYS_ADMIN` would be needed). Carried into S9/S10 as the load-bearing
finding of this spike.
