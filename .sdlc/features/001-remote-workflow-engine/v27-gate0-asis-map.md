`model-catalog.ts` builds the raw federated catalog: `ModelEntry` (`:11-61`, fields: `provider`, `model`, `aliases?`, `description`, `modalities`, `contextWindow`, `price`, `toolUse`, `location`, `ref?`, `besteffort?`, `ratesPerM?`, `effortDeclared?`, `declaredSource?`, `supported_parameters?`) — no `latency`/`benchmarks` field exists anywhere in this interface. `buildCatalog(opts)` (`:292-311`) federates a static Anthropic table + live Ollama `/api/tags` + live OpenRouter `/api/v1/models`, each independently timeout-guarded. `enrichModelEntry(e, catalogFetchedAt?)` (`:419-442`) produces `EnrichedModelEntry` (`:341-360`: adds `capability`, `stability`, `costLevel`, `toolUseDeclared`, `effortDeclared`, `declaredSource`, `catalogFetchedAt`) — this is the exact shape `GET /api/models` returns. `filterCatalog(entries, filter?)` (`:446-467`) AND-filters + caps at `limit` (default 100, hard cap 500).

## D. Constraints an implementer would trip on

1. **`no-skeleton-surface` allowlist is exactly six files** (`no-skeleton-surface.test.ts:53,82`) and none of the dashboard-surface files in this scope (`dashboard-page.ts`, `workflow-view.ts`, `run-view.ts`, `system-info.ts`, `src/models/*.ts`) are on it. A rewrite must not introduce the word "skeleton" (case-insensitive, comments included) anywhere in those files.
2. **The dashboard's `/api/*` surface is entirely unauthenticated by construction**, dispatched (`server.ts:1284-1294`) before any Host/Origin/bearer check that applies to other routes; `auth.enabled` only ever changes what a route DISCLOSES (e.g. the DAG route's skeleton-overlay masking at `server.ts:509-520`), never whether it responds at all (rationale documented at `server.ts:1235-1243`, citing issue #57 / ADJ-A1 being overruled — hiding existence bought nothing because `/api/workflows` already discloses everything anonymously). Any v27 addition of new dashboard data (e.g. new fields on `/api/runs`) inherits this: it is public to anyone who can reach the port.
3. **CSP is per-route, not global.** Only `GET /api/workflows/:name/diagram.svg` sets `Content-Security-Policy`/`X-Content-Type-Options` (`server.ts:444-454`) — the `<img>`-only-never-`<object>`/`<embed>` load path is what keeps an author-authored SVG from executing script (REQ-119/ADR-033's surviving reason). `GET /dashboard` itself sets no CSP header at all (`server.ts:1254`, plain `text/html`).
4. **Offline / no-CDN stance is load-bearing and test-locked**: no Mermaid library, jQuery, chart library, or any external script/CSS reference exists anywhere in `DASHBOARD_HTML` — confirmed by `dashboard-diagram-render.test.ts`'s explicit CDN/`mermaid.min.js` grep guards. A v27 rebuild that wants a component framework or a charting library must either vendor it into the served page/bundle or get this constraint formally revisited — it is currently enforced by tests, not just convention.
5. **`textContent`-only invariant on every run/author-derived string** — repeatedly restated across DES-065/133/156/184/etc and directly tested (dashboard-diagram-render.test.ts's `innerHTML` absence checks, workflow-page-harness-table's cell construction via `textContent`). Any new UI surface (agent-detail slide-in panel, sortable model table, etc.) touching run- or workflow-author-supplied strings must keep this.
6. **The `.zoomable` transform lives on the WRAPPER, never on children `renderGraph()`/`renderDiagram()` rebuild every 3s poll** (`dashboard-page.ts:687-692` comment) — this is the mechanism that lets a user's zoom/pan survive the poll; a new swimlane graph component must preserve an equivalent separation (transform-holder vs. re-rendered content) or the zoom will visibly reset every 3 seconds.
7. **DAG cap**: `layoutGraph`'s `maxNodes` defaults to 200 (`dashboard.ts:343,272` companion `DAG_BOX_DEFAULTS`), truncating with a `warnings[]` entry (`dashboard.ts:442`) rather than ever emitting an unbounded graph.
8. **The `/dashboard` static page hardcodes ONE Morandi light palette** (`dashboard-page.ts:107,120,573`, etc.) baked directly into a template-literal `<style>` block that also contains the client JS. There is no CSS variable indirection point for a runtime theme switch or accent-hue slider today — introducing one means restructuring how `DASHBOARD_HTML` is assembled (or moving to a real asset pipeline), which is itself a decision the next gate should make explicitly, not something achievable as a drop-in CSS var override.
9. **Fixed 3s poll, no SSE/websocket** (`dashboard-page.ts:733`) — VAL-018 (`tests/acceptance/val-018-dashboard-browser-ui.test.ts:66`) accepts "SSE or polling", so switching transport is allowed by the acceptance contract, but every render function assumes a full-refetch-on-tick model today (no incremental diffing).
10. **Duplicate server/client logic (see §A's "Duplicate candidates")** is a structural consequence of shipping the entire client as one server-side template literal with no build step — any v27 architecture change (e.g. a real bundler, a separate static asset) should treat collapsing these duplications as an explicit, welcome side-effect, not something to silently reproduce again in a new form.

## E. Gap verdicts for the new design's five named API needs

| Need | Verdict | Evidence |
|---|---|---|
| `GET /api/runs/:id/dag` carries `lanes:[{index,title}]` | **Partially exists, with a caveat** | The shape already exists SERVER-SIDE as `ExpectedLane {index, title, dynamic, slots}` (`skeleton-graph.ts:25-30`), computed via `deriveExpectedGraph` and consumed by `layoutGraph` (`server.ts:519-544`, `dashboard.ts:334-461`) to place cells into columns (`col = lane.index + 1`, `dashboard.ts:363`) — but it is discarded after layout; the response payload today is `{kind:'run', cells, edges, warnings, truncated?, startedBy, terminalAt?}` (`server.ts:546-552`) with NO `lanes` key. **Caveat**: `expectedGraph` (and therefore its `.lanes`) is only populated `if (!authEnabled)` (`server.ts:520`); under auth it stays `{lanes:[], slots:[], edges:[]}` (`server.ts:519`), so serializing `expectedGraph.lanes` directly would go empty exactly when auth is on. The always-available alternative source for lane titles is `view.phases[].title` (`types.ts:293-298`, `PhaseView`) — REQ-128's own rule is "one lane per phase" (§B), so a v27 implementation should derive `lanes` from `view.phases` (present regardless of `authEnabled`) rather than from the masked `expectedGraph`, or explicitly decide the lanes array should also be masked under auth. Either way, closing this gap is a small serialization addition at `server.ts:546-550`, not new data-modeling work. |
| `GET /api/runs` summaries carry `costUSD` | **Missing** | `RunSummary` (`types.ts:358-369`) has exactly `{runId, name?, status, scriptVersion, createdAt, startedBy?, terminalAt?}` — no cost/usage field, and `store.listRuns()` (`run-store.ts:369`, called at `server.ts:363,387`) returns exactly that type with no enrichment. The per-run `costUSD` DOES exist, but only inside `RunUsage` on the single-run detail endpoint (`/api/runs/:id`'s `usage` field, `types.ts:352-355`) — the list endpoint would need either a new per-run fold-and-attach step or a persisted summary column; this is real backend work, not just serialization. |
| `GET /api/runs/:id/agents/:agentId` returns `{record, harness, events}` | **Partially exists / needs one field added** | `harness` and `events` are already returned under those exact names by the route today (`server.ts:555-570` → `mcp-facade.ts:664-700`, returning `{runId, status, harness: HarnessDescriptor\|null, events: TranscriptEvent[], result, hasMore}`). There is **no `record` field**: the matched `AgentRecord` (`agentId, label, state, provider, model, tokens, costUSD, unpriced, startedAt, endedAt, frame, ...`, `types.ts:215-291`) is already resolved and held in a local variable (`agent`, `mcp-facade.ts:677-683`) but never included in the object built at the return statement (`mcp-facade.ts:699`). Closing this gap is localized to one line: add `record: agent` to that return object. |
| `GET /api/models` carries optional `latency:{ttftMs,p50Ms}` | **Missing** | No `latency`, `ttftMs`, or `p50Ms` token appears anywhere in `src/models/*.ts` or `src/server.ts` (confirmed by grep). `ModelEntry`/`EnrichedModelEntry` have no timing fields at all, and no live probing of per-model latency exists in the catalog-build pipeline (`buildCatalog`, `model-catalog.ts:292-311`, only fetches capability/pricing metadata, never round-trips a real call). This would be new instrumentation (either a probed metric persisted somewhere, or an OpenRouter-supplied stat if one exists upstream — not currently parsed even if present in the raw feed at `model-catalog.ts:210-251`). |
| `GET /api/models` carries optional `benchmarks:{name:score}` | **Missing** | Same evidence as above — no `benchmarks` token anywhere in the models code, no static or live source feeds anything resembling a named benchmark score today. This is a new data source (either a new static curated table alongside `STATIC_ANTHROPIC`, `model-catalog.ts:143-148`, or a new external feed) plus a new field threaded through `ModelEntry`→`EnrichedModelEntry`→the wire. |
