## Verdict

**consistent: no — 16 deviations** (2 HIGH, 7 MEDIUM, 7 LOW). The v24 skeleton the architecture promised — one `TOOL_SPECS` array, one `authorize()` before the switch, one `pathVerdict`, principal-derived CAS namespace, HMAC-before-claim-state, audit-before-bytes, `composeConfig` forwarding with a fail-closed `principals` default — is in place and matches. The deviations cluster where the architecture said something was *removed, dropped or migrated* and the code kept a second copy instead: the `workflow` column beside `claimedBy`, the create-time trigger door beside the claim door, `workflow_diagrams` beside `mermaid`, a raw SQL handle beside the store port, `args.principal` beside `Principal`, hardcoded `DEFAULT_CEILINGS` beside the resolved ceilings, and — most consequentially — no migration of the legacy asset tree beside a GC that now sweeps it.

## Findings (severity-first)

### F1 — HIGH — Legacy assets and `mcp_provisions` are never migrated, and the first GC tick after upgrade deletes the pre-v24 global skill tree
**Violates:** ARCH-098 ("Legacy assets in the pre-v24 global tree are migrated at boot into `assets(workflow='', pushedBy='legacy')` rows, `mcp_provisions` rows likewise with `kind:'mcp'` and their `config` — transactional and idempotent"), ARCH-102 ("`mcp-registry.ts` and its `mcp_provisions` table are retired (rows migrated by ARCH-098)"), Deployment view (iv) ("boot migrations: … global-tree assets and `mcp_provisions` → `catalog.assets` with `pushedBy:'legacy'`"), decision rationale ("QD-R4 (legacy assets owner-less) — migrated as global `pushedBy:'legacy'` rows").
**Evidence:**
- Absence: `grep -rn "mcp_provisions\|'legacy'\|\"legacy\"\|migrat" src/` finds no asset or provision migration — the only `migrat` hits are the v15 owner backfill and the v22 `workflow_versions` migration (`src/workflow-catalog.ts:158-225`). `putAsset` (`workflow-catalog.ts:264-274`) has exactly one production writer, `AssetSyncService.push`.
- Pre-v24 layout (boundary read, `git show c9c6592:src/gateway/claude-agent-sdk-client.ts` lines 155-176): global skills lived at `<assetRoot>/skill/<name>` with `assetRoot = <workRoot>/assets` (`git show c9c6592:src/server.ts:2115`).
- v24 layout: `defaultAssetRoot(workRoot) = <workRoot>/assets` (`src/asset-sync.ts:139-141`), workflow scope at `<assetRoot>/<workflow>/skill/<name>` (`:242-243`); global scope moved to `<workRoot>/_global_assets` (`:143-146`).
- GC: `reclaimStaleWorkspaces` now receives `hasWorkflow` and the resolved `assetRoot` unconditionally (`src/server.ts:847`) and deletes every child of `<assetRoot>/` whose name is not a live workflow (`src/workspace-gc.ts:66-88`). The legacy directory `<workRoot>/assets/skill/` is such a child.
**Consequence:** on a pre-v24 deployment the upgrade (i) makes every previously provisioned MCP config unresolvable (`resolveMcp` reads only `catalog.assets`, `src/asset-sync.ts:200-216`), so scripts declaring `mcp:[…]` get `missing` on every dispatch with no error, and (ii) destroys the operator's global skills on the first GC sweep. Audit ≠ containment was this lens's own ADR-030 argument; here the reverse holds — the architecture promised the data would be carried and the code silently drops it. Security lens: silent capability loss in agents that previously had an MCP server is a behaviour change nobody is told about. Consistency lens: the deployment view's operator promise is false.

### F2 — HIGH — A version that declares zero triggers is stored as `triggers NULL`, so `NOT_IN_RELEASE` can never fire and moving `release` cannot un-declare a trigger
**Violates:** ARCH-098 ("`triggers TEXT NULL` (JSON `string[]`; both `NULL` **only on pre-v24 rows** — ADR-025/026)"), ADR-026 ("`workflow_publish` moving `release` changes the effective trigger set"; "the fire path resolves `release` and checks the version's `triggers` (legacy `NULL` list ⇒ member)"), ARCH-099 ("the release version's `triggers` is non-`NULL` and does not contain this id → `NOT_IN_RELEASE`").
**Evidence:** `src/workflow-catalog.ts:472` `const triggersJson = triggers && triggers.length > 0 ? JSON.stringify(triggers) : null;` — `workflowRegister` always passes an array (`src/mcp-facade.ts:300`, `:325`), so a post-v24 version with `triggers: []` is written `NULL`, byte-identical to a pre-v24 row. `resolveDetail` only surfaces `triggers` when non-null (`:615`). Both fire paths then skip the membership check: `src/server.ts:775` `if (released.triggers !== undefined && …)` and `src/webhook-registry.ts:279`.
**Consequence:** author registers v1 with `triggers:[t1]` (claim held), then v2 with `triggers:[]` and publishes v2 to `release`. ADR-026 says t1 must now be refused `NOT_IN_RELEASE` and recorded. Instead t1 keeps firing v2 — the claim is `held` from v1 and never released (`src/mcp-facade.ts:320`). The "versioned trigger set" the requirement exists for is not versioned in the one direction that removes a trigger. Consistency lens: HIGH — the coalesced-refusal machinery (ADR-031) is correct but unreachable for this case. Fix is one line (`JSON.stringify(triggers ?? [])`, never `null` on a post-v24 row) plus the test ARCH-098 itself asked for ("another asserts no post-migration row is written `NULL`") — that test cannot exist today for `triggers`.

### F3 — MEDIUM — `authorize()` admits an admin re-registering another author's workflow; the catalog then refuses it — the table and the store disagree
**Violates:** ARCH-088 matrix ("`admin` — everything, ownership bypassed (owner ruling)"), ARCH-088 note ("the table decides, the store re-asserts, a disagreement between the two is a test failure not a policy"), ADR-024 (authz row on the spec, checked once).
**Evidence:** `workflow_register` row is `{minRole:'author', ownership:'none'}` (`src/tool-specs.ts:213`), so `authorize()` never consults `workflowOwner` for it. The facade then hands `attributionWithArg(principal, a)` — the admin's **own id**, never a bypass (`src/mcp-facade.ts:180-184`, `:316`, `:325`) — to `validateRegistration` and `insertVersion`, both of which refuse `existing.owner !== principal` (`src/workflow-catalog.ts:454-455`, `:477-478`). `workflowPublish`/`workflowDeregister` use `bypassWithArg` (null for admin) instead (`:349`, `:392`).
**Consequence:** an admin cannot register a new version of a workflow it does not own (`NOT_WORKFLOW_OWNER`), while it can publish, deregister and read it. It is a denial rather than a grant, so MEDIUM not HIGH — but it is exactly the class ARCH-088 said must be a test failure, and no test caught it because the register row delegates ownership to the store. The clean fix is the one the tri-state `OwnerLookup` was built for: `workflow_register` with `key:'name'`, `ownership:'workflow'` (`undefined` = new name ⇒ ok; owner ≠ caller ⇒ `NOT_WORKFLOW_OWNER`; admin ⇒ ok), and the catalog receiving the bypass identity for the owner gate and the caller identity for attribution as two separate arguments.

### F4 — MEDIUM — Two trigger-binding doors and two binding columns where ARCH-099/100 specified one
**Violates:** ARCH-099 ("`create(spec)` takes no workflow …; the `workflow NOT NULL` column is migrated (`claimedBy = workflow`, then dropped)"), ARCH-100 ("`create()` takes no workflow"), ADR-026 ("Who may claim: the trigger's creator or an admin"), ARCH-091 (`workflow_register` is where the claim happens).
**Evidence:**
- `schedule_create`/`webhook_create` schemas carry an optional `workflow` (`src/tool-specs.ts:646`, `:715`); both rows are `ownership:'none'` (`:667`, `:719`). `SqliteSchedulerPort.create` writes `workflow: s.workflow ?? null` AND `claimedBy: s.workflow ?? null` (`src/scheduler.ts:234-238`, comment `:21-23` "the pre-v24 door, kept"); `WebhookRegistry.create` writes `workflow` directly (`src/webhook-registry.ts:158-159`).
- The `workflow` column is not dropped; the two columns are folded at four sites: `all()` `:349` `claimedBy ?? workflow ?? ''`, `release()` `:438` clears both, `claimedIdsFor()` `:271` `claimedBy = ? OR workflow = ?`, `rearmAtBoot()` `:478` `WHERE … workflow IS NOT NULL` — which excludes rows claimed through the register door (`claim()` writes only `claimedBy`, `:420-422`), so `all()` and `rearmAtBoot()` disagree about which rows exist.
- IMPL-187 D-1b records the live consequence: a released schedule kept firing via the `workflow` column and re-fired for a same-name re-registration 47 s after deregister.
**Consequence:** (security) an author binds a cron to *any* workflow, including another author's, at creation with no workflow-owner check — ADR-026's "creator or admin" rule governs who claims a trigger but the create door lets the trigger's creator bind to a workflow they do not own, and `run_start` being open to `user` does not make this equivalent: the binding shows up in the owner's `workflow_describe.triggers[]`, is released by the owner's `deregister`, and fires with the creator's `args`. (consistency) with F2, a create-door binding is never in any version's `triggers[]`, so it is the one shape where `NOT_IN_RELEASE` semantics were *designed* to be skipped — the code comment at `server.ts:771-774` rationalises F2 by pointing at this door. Karpathy: one concept, two columns, four fold sites — the architecture's "migrate then drop" was the simpler design and it was the one written down.

### F5 — MEDIUM — `checkMermaid` enforces a different grammar from ARCH-097: the `<`/`>` restriction is not checked, the value triple is optional, and `DIAGRAM_VALUE_MISMATCH` does not exist
**Violates:** ARCH-097 ("agent node text matches `^(?<label>…)<br/>(?<model>…) · (?<effort>…) · (?<timeout>…)$`"; "**Security**: … `<`/`>` are now legal only inside the two tokens `<br/>` and `<-->`"; codes `DIAGRAM_VALUE_MISMATCH`, `valueMismatch[]`; header `flowchart|graph <TD|TB|LR|RL|BT>`; `subgraph ID ["title"]` with optional `direction`), ADR-029 ("that entry must carry defaults for the three tunables … which is also what makes ARCH-097's value-triple compare sound (there is always a declared value to compare the picture against)"), decision rationale ("Value-triple compare — adversarial only; adopted").
**Evidence:** `src/check-mermaid.ts:40-49` every node regex captures `(.*)` — no character restriction on any shape's text; `:196-198` `if (parts.length < 2) continue; // no meta on this node — nothing to compare` makes the triple optional; the shipped fixture `FIXTURE_MERMAID = 'graph TD;\ngreet(["greet"])'` (`src/tool-specs.ts:121`) has no triple and registers; `:210` emits rule `VALUE_MISMATCH`, which `workflow-catalog.ts:435-436` maps to the generic `MERMAID_INVALID` — `grep DIAGRAM_VALUE_MISMATCH src/errors.ts` is empty; `:50` `HEADER_RE = /^(graph|flowchart)\s+\S+$/` accepts any direction token (and `graph TD;`); `:51` `SUBGRAPH_RE = /^subgraph\s+"([^"]*)"$/` admits no ID and no `direction` line; `:112` recognises the header only at line 1, so a leading `%%` comment makes the header `MERMAID_INVALID`.
**Consequence:** (security) the defence-in-depth the architecture stated for author-controlled text served to every principal is absent; ADR-033's `textContent` is now the *only* layer, and ARCH-106's grep guard is what keeps it so. (consistency) "picture says opus, meta says haiku" is prevented only when the author volunteers the triple; omission is the easy drift and it is admitted. The guide interpolates `SHAPES`/`EDGE_FORMS` from this file, so the *guide* is right and ARCH-097 is the stale party for header/subgraph — but the triple-optional and `<>` points are the architecture being right and the code weaker.

## The three lenses in conflict — argued explicitly, with the Karpathy tie-break

**C1. Sync `OwnerLookup` port (testability) vs. second DB handles with duplicated paths (consistency/simplicity) — F8.**
Testability wanted `authorize()` pure and synchronous so unit tests pass a `Map`; the stores are async ports. The implementer resolved the tension by opening raw connections. Security is indifferent (same rows, WAL). Consistency loses: the store layout is now spelled in two places, the exact bug class this iteration paid for with `assetRoot`. Karpathy tie-break: the *minimum* change that keeps the pure function is the sync `getOwner` ARCH-092 already specified, on the two concrete stores (better-sqlite3 is synchronous underneath, so no async port change is needed) exposed through a narrow port — one method per store, zero new connections, zero duplicated paths. Testability keeps its `Map`; consistency keeps one layout. **Testability's *goal* wins; its *implementation* here does not.**

**C2. Kept create-time binding door (consumability/back-compat) vs. one claim model with an owner gate (security/consistency) — F4, F2.**
Consumability argued (in code comments, not in the ledger) that pre-v24 callers pass `workflow` at creation and removing it breaks them. Security says the create door has no workflow-owner check and inverts ADR-026's direction of claim. Consistency says it forces a second column, four fold sites, and the `[] ⇒ NULL` collapse that defeats `NOT_IN_RELEASE`. The owner already ruled "no deprecation window" for tool names (ARCH-087); a positional argument does not deserve more tenure than a tool name. Karpathy tie-break: one column, one door; if back-compat is wanted, `schedule_create({workflow})` should be sugar that *calls* `claim()` after an ownership check, not a parallel write path. **Security and consistency win; consumability is served by the sugar, not by a second model.**

**C3. Pure `parseParamContract` with no ceilings threaded (simplicity) vs. operator ceilings honoured on defaults (security) — F6.**
Simplicity kept the registration parser dependency-free and used the exported constant. Security says the ceiling is the operator's cost/abuse control and it now binds only overrides. Scalability is indifferent. Karpathy tie-break: threading one argument the catalog already holds (`this._ceilings`) is smaller than the second enforcement site run-manager would otherwise need; "single exported source" (ARCH-094) means one *default*, not one *value at every site*. **Security wins at the cost of one parameter.**

**C4. `loopback-exempt` row-shape rule (consumability of the D-BIND rescue path) vs. least privilege (security) — not counted as a violation.**
`src/authz.ts:87-90` implements ARCH-088's rule exactly: `minRole:'user' && ownership:'none'` ⇒ ok. That shape admits `run_start` (spends budget, `src/tool-specs.ts:387`), `workspace_push` CAS mode (`:536`, writes into the shared `'local'` pool), `workspace_diff`, `issue_report`/`issue_comment_post` (posts to GitHub, `:770`, `:810`) for an unauthenticated loopback socket on an auth-enabled server bound to `0.0.0.0`. The architecture chose a *shape* as a proxy for "read-only and harmless", and the shape is not that. The implementation is faithful, so this is an architecture-quality note, not a deviation: an explicit `loopbackExempt: true` flag on the handful of rows the rescue path needs (the v15 rationale was self-update/status) would be both narrower and more honest than a structural proxy. **Recorded for the owner; Karpathy says one boolean per row beats a rule that must be re-derived.**

**C5. Audit read-back (observability) vs. no viewer (scope) — held.**
ADR-027's compromise (table + `run_status.adminReads[]`, no new tool) is implemented as written: `auditedWorkspaceRead` appends before the read and rethrows on failure (`src/audited-read.ts:273-284`); `adminReads` is attached only for the owner (`src/mcp-facade.ts:570-571`). No conflict remains.
