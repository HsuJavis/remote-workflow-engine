## Summary

**Altitude decision first.** v26 is a mixed slice and I split it rather than force one altitude. **Agent
altitude** (the consumer or the subject is a model, not an operator): REQ-122 — *observability of a model
call's failure* (the engine must say "401 authentication_failed on openrouter" within one attempt, not
"timeout" after 240 s); REQ-123 — *replaceability* (three provider paths that are interchangeable with no
per-provider tool patch is what lets a workflow survive a model swap); REQ-126 — the agent's own *quality dial*
(effort must reach the wire or be honestly reported as not applied); REQ-127 — *self-sustainability in money*
(a budget that counts 18 of 40,000 input tokens is not a budget) and per-call cost as agent-altitude
observability; REQ-128/130 — *consumability where the author is a cold model* (the guide and the refusal
envelope ARE the API; REQ-117's first-try success is the acceptance). **System altitude:** REQ-121 (input
validation that fails closed), REQ-124 (a read-side layout defect), REQ-125 (record integrity), REQ-129
(rendering). I do not argue agent-altitude observability for the dashboard or system-altitude scaling for
the guide.

**The slice in one sentence.** v26 is four corrections and two structural additions. The corrections: a seed
element without bytes is refused before any write (REQ-121); a provider's terminal error ends the attempt
and kills the CLI subprocess (REQ-122); the terminal agent record keeps what the harness resolved (REQ-125);
the run DAG gets the phase from the run's own timeline — snapshotted at IPC receipt, carried on the harness event the journal already writes — not from an option nobody sets (REQ-124). The additions: **one pure
derivation `skeleton → expected {lanes, slots, edges}`** consumed by both the registration checker (REQ-128)
and the run-DAG layout (REQ-124) so the two can never disagree about what a script's shape is; and **one
`ModelBook`** — a TTL'd, single-flight snapshot of the catalog that answers "what does this model cost per
token (four rates)" and "does it declare reasoning/tools", pinned onto the run row at admission, consumed by
the budget (REQ-127), the effort wiring (REQ-126) and `models_list` (REQ-126/130) so all three see the same
numbers. Everything else is deletion (openai, gemini, the Read exclusion, two dead effort tables) and
generated text. **Zero new services, zero new runtime dependencies, one new SQLite column on
`workflow_versions` (`diagram_contract`), one on `runs` (`price_book`), three new pure files
(`providers.ts`, `skeleton-graph.ts`, `models/model-book.ts`), and a net negative line count.**

**Where my three lenses actually fight** (argued in §Conflicts): a USD budget that silently replaces a token
budget under the same field name (security: a safety control that reads as armed and is not) vs the REQ's
literal `budget: number` (simplicity); a budgeted run whose model cannot be priced — refuse at the door
(security fail-closed) or `costUSD:null` and count (REQ literal, self-sustainability); a boot refusal for
retired providers (security) vs REQ-070's "never leave the service down" under an auto-restarting updater;
an exact AST for the skeleton (testability, security) vs no `typescript` runtime dependency (simplicity);
a server-side SVG string for the run DAG (testability) vs the client's `textContent`-only construction
(security); classifying provider errors by status set (REQ literal) vs by the SDK's closed error-kind union
(testability, and it closes the old thinking-400 four-minute class).

**Two deviations from REQ-127's literal text and one extension of REQ-122 are proposed and FLAGGED for a
ruling, with the REQ's own reading as the fallback** (ADR-037, ADR-038, ADR-040). Nothing else in this
proposal narrows an owner ruling.

### ARCH-110 — `validateSeedSpec`: every `seed` element is checked before any byte is written; the schema describes all three seed shapes
- **traces:** REQ-121, REQ-025, REQ-065, REQ-082
- **module:** src/workspace-seed.ts (pure validator + materializer), src/tool-specs.ts (schema), src/mcp-facade.ts / run-manager admission (call site)
- **deps:** ARCH-007, ARCH-093 (`pathVerdict`), ARCH-087 (`TOOL_SPECS` is the schema)
- **api:** `validateSeedSpec(seed: unknown) → { ok: true; files: SeedFile[] } | { ok: false; code: 'INVALID_SEED_SPEC'; path: string; index: number; hint: string }` — refuses the FIRST element whose `contentB64` is not a string (or whose `path` is not a string), `hint` = "seed carries bytes inline; to seed by sha256 use seedManifest (blobs pushed via workspace_push) or seedManifestRef". `materializeSeed` takes `SeedFile[]` from a passed validation and THROWS (never `?? ''`) if a non-string reaches it — defence in depth, not the primary gate. `run_start.seed.items = { type:'object', required:['path'], properties: { path: {type:'string', description}, contentB64: {type:'string', description:'REQUIRED — base64 of the file bytes…'} } }`, `seedManifest.items = { required:['path','sha256'], properties: { path, sha256: {pattern:'^[0-9a-f]{64}$'}, exec: {type:'boolean'} } }`, `seedManifestRef: {type:'string', pattern:'^[0-9a-f]{64}$', description}`. `additionalProperties:false` on `seed.items` is applied ONLY after the plugin client `push_workspace.py` is confirmed to send exactly `{path, contentB64}` (REQ-121's own precondition; Gate 5 reads the plugin repo).
- **Security:** the current path writes as it iterates — a malformed element mid-list leaves a half-materialized workspace that agents then run on (issue #64's five empty runs are this, in the degenerate all-empty case). Validate-all-then-write makes the seed atomic with respect to spec errors; path containment (`pathVerdict`) stays per-file. Base64 decode of garbage is NOT refused (Node decodes leniently) — deliberately: a byte-exactness guarantee belongs to `seedManifest`'s sha-verified route, and saying so in the description is cheaper than a second decoder.
- **Scale/consistency:** none; O(n) over the list, before the first `mkdirSync`.
- **Testability:** the red test is `validateSeedSpec([{path:'a', sha256:'…'}])` → `{ok:false, code:'INVALID_SEED_SPEC', path:'a', index:0}`; the integration test asserts `run_start` refuses AND the workspace directory does not exist / has no files.
- **Karpathy:** why not `required:['path','contentB64']` in the schema and let ajv refuse? Because ajv's refusal is `INVALID_ARGUMENT` and the REQ wants a named code with the `seedManifest` pointer; the post-schema validator with a specific code is the existing pattern (`SEED_SOURCE_CONFLICT`, tool-specs.ts:401). The schema still DOCUMENTS `contentB64` as required in its description so `tools/list` tells the truth; a keyword→code translation layer in `call-tool.ts` would be the speculative alternative.

### ARCH-111 — provider errors end the attempt: `classifyApiError`, `_drain` reads `system/api_retry`, the controller always exists and is always aborted, `GatewayResult.retryable:false` stops the retry loop
- **traces:** REQ-122, REQ-020, REQ-037, REQ-038
- **module:** src/gateway/claude-agent-sdk-client.ts, src/gateway/client.ts (`GatewayResult` type)
- **deps:** ARCH-005, D-F7 (bounded race), D-F10(c) (`Options.abortController` is the only thing that kills the CLI subprocess), ARCH-056 (redaction at capture)
- **api:** `classifyApiError(kind: SDKAssistantMessageError, status: number | null) → 'terminal' | 'retry'` — pure, total over the SDK's closed union: `authentication_failed | oauth_org_not_allowed | billing_error | invalid_request | model_not_found → 'terminal'`; `rate_limit | overloaded | server_error | max_output_tokens → 'retry'`; `unknown → status in 400..499 and not 408/429 ? 'terminal' : 'retry'`. `GatewayResult` (failure arm) gains `retryable?: false` and `error?: { kind: string; status: number | null; attempt: number }`. `_drain(session, model, onEvent, abort: () => void)`: on `msg.type === 'system' && msg.subtype === 'api_retry'` with a `'terminal'` classification → emit `{kind:'message', data:{type:'error', detail:'<provider> <status> <kind>: <error text>', status, kind, attempt}}` (streamed via `onEvent` when present, else pushed) and return `{ok:false, reason:'terminal', retryable:false, detail, error, events}`; a `'retry'` classification is recorded as an event and the loop continues (the CLI's own backoff is left alone; the engine's `timeoutMs` still bounds it). `_invokeOnce` creates the `AbortController` UNCONDITIONALLY and calls `controller.abort()` in its `finally` after the race settles — idempotent, harmless after a normal `result`, and the only way a fast terminal also stops the CLI's remaining nine retries. `invoke()`: `if (!last.ok && last.retryable === false) break;`. The direct-fetch gateway already returns terminal on 4xx; it gains the same `retryable:false` on 401/403/404 so both clients honour one contract. **Record side (REQ-122's "AgentRecord 為 failed 並帶同一 detail"):** `AgentRecord.detail?: string` is a NEW field (types.ts:116-149 has none today), present on `failed` only, written by `capture()` from `result.detail`. It is a NEW PERSISTED STRING and is treated as one: it reaches disk through snapshot sink (2) (`run-manager.ts:880` — `redact()` walks nested strings, so the existing call covers it) and through the error event on sink (1); it is CAPPED at `MAX_ERROR_DETAIL_BYTES = 1024` **after** redaction, never before (R-G9: a cut before `redact()` can split a secret and defeat the value-exact match); it is added to `redact-sweep.test.ts`'s sink list and to the `run_status` agent projection. **Unmapped `system` subtypes are COUNTED, never stored:** `_drain` keeps a per-attempt `Set<subtype>` of `system` messages it did not classify and returns it as `GatewayResult.unmapped?: string[]`; `capture()` folds it into `run_result.meta.unmappedMessages: Record<subtype, count>`. That is the whole concession to "the next silent drop must be visible" — a name and a count, no payload (see C10).
- **Security:** the `detail` string carries the CLI's error text, which is provider response text — it goes through the same transcript path every event does and is therefore redacted at capture (REQ-083). Fail-fast on 401/403 does not change the auth surface (the key never leaves the subprocess env). What it removes is a *masking* defect: a revoked key looked identical to a slow model. Two things stated so nobody rediscovers them: (1) the LIVE `run_status` reply is served un-redacted by design (DES-088 persist-only redaction) — the caller is the run's owner, the text is a provider error body, and the 1024-byte cap bounds it; every PERSISTED copy is redacted. (2) Capturing every unmapped SDK payload (the observability lens's instinct) is declined on this lens's grounds: provider response bodies are the one input stream the engine does not author, and widening what it stores of them widens the exfiltration surface for exactly the class REQ-083 exists to close — the subtype counter above is what is kept.
- **Scale/consistency:** today a 401 holds a RunGuard concurrency slot and a host `AgentSemaphore` permit for `timeoutMs × (1+retries)` while a CLI subprocess retries ten times against a provider that has already said no — on a 24-wide `parallel()` that is 24 dead subprocesses for four minutes. The race-order subtlety is real and is why the abort lives in `finally`, not inside `_drain`: `bound` resolves synchronously on `abort()`, so an abort issued *inside* `_drain` before it returns can let `bound` win `Promise.race` and misreport `reason:'timeout'`. `_drain` returns; then `_invokeOnce` aborts.
- **Testability:** `fakeSession` yields `{type:'system', subtype:'api_retry', attempt:1, max_retries:10, retry_delay_ms:500, error_status:401, error:'authentication_failed'}` forever and never a `result` → assert terminal within one attempt, `events.length ≥ 1` with `data.type==='error'`, `options.abortController.signal.aborted === true` after `invoke()` resolves, and `queryImpl` called exactly ONCE (the loop broke). A second case with `rate_limit`/429 asserts the loop does NOT break and the timeout still bounds it. `classifyApiError` gets a table test over the whole union — `Record<SDKAssistantMessageError, …>` is total, so a new SDK kind is a `tsc` error, not a silent `'retry'`.
- **Karpathy:** one pure classifier, two lines in the loop, one unconditional controller. No circuit breaker, no per-provider health table, no retry policy object. The alternative "make the engine's retry loop smarter" is exactly the speculative machinery this avoids: the CLI already retries; the engine's only job is to recognise *cannot succeed* and stop.

- **module:** src/skeleton-graph.ts (new, pure), src/workflow-meta.ts (`SkeletonNode.alt`, `AgentCallScan.calls[].allowedTools`)
- **deps:** ARCH-096 (`scanAgentCalls`), ARCH-097 (`checkMermaid`), ADR-029 (literal labels, statically decidable or refused), ADR-039
- **api:** `interface ExpectedGraph { lanes: Array<{ index: number; title: string | null; slots: number[] }>; slots: Array<{ index: number; lane: number; labels: string[]; kind: 'single' | 'parallel' | 'alt'; tools: Record<label, string[] | 'default'> }>; edges: Array<{ from: number; to: number }> /* consecutive slot indices */ }`; `deriveExpectedGraph(nodes: SkeletonNode[], scan: AgentCallScan) → ExpectedGraph | { refused: 'AGENT_OUTSIDE_PHASE'; line: number; label: string }`. Rules, in order: (L1) one lane per `phase` node in source order; `title` is the literal when `STRING_ARG_RE` matched, else `null` (dynamic title — matched by POSITION downstream). (L2) an `agent()` before the first `phase()` is REFUSED under the v2 contract (`LANE_MISMATCH`, "agent 'x' at line N runs before any phase(); every agent must be dispatched inside a phase") — a swimlane with an unnamed zeroth lane is not checkable and not drawable. (S3) NEW `alt` group id on `SkeletonNode`: `agent()` calls that are the two arms of one `cond ? … : …` expression, or that sit in the `{}` blocks of one `if (…) {…} else {…}` statement, at the same delimiter depth — detected with the string-aware `matchDelimiter` the skeleton scanner already uses → one `alt` slot with the candidate label set. (S4) `kind:'workflow'` skeleton nodes (nested `workflow()`) are TRANSPARENT: no slot, no edge constraint; a `parallel()` whose members are all `workflow()` calls yields no slot. (T1) `tools[label]` = the literal `allowedTools` array from `scan.calls[]` (sorted) when present, `[]` → `'none'` is spelled by the consumer, absent → `'default'`. (E1) an edge between every pair of consecutive slots, across lane boundaries too (last slot of lane k → first slot of lane k+1). Nothing else is modelled: a `switch`, an `agent()` inside a loop body, an `agent()` reached through a helper function, are either already `SCAN_VIOLATION` (non-literal label) or fall under ADR-039's "undecidable → refused" with a line-pointed message.
- **Security:** none new — pure text analysis, no I/O; the checker that consumes it stays the only gate on author text, and the renderer downstream keeps `htmlLabels:false` (ARCH-109).
- **Scale/consistency:** the load-bearing property is *one derivation, two consumers*: `checkMermaid` v2 (ARCH-119) verifies the author's diagram against it at registration; `layoutGraph` (ARCH-114) places live agents by it at read time. Before v26 the checker knew nothing of phases and the layout knew nothing of the checker — issue #67 (edges unchecked) and #70 (every agent frame-grouped) are the same missing object seen from two sides. Nested frames: a nested workflow's own `phase()` calls push onto the PARENT run's `entry.phases` (run-manager.ts:924), so a composite run can emit more runtime phases than the top-level skeleton has lanes — the layout appends extra lanes with a warning rather than mis-joining (REQ-124 records this as the known approximation).
- **Testability:** fixtures are `(script, expectedGraph)` pairs, no server: sequential three agents; two phases; `parallel()` of three; a ternary; an if/else; a dynamic phase title; an agent before the first phase (refused); a nested `workflow()` inside a phase (transparent); `parallel()` of two `workflow()` calls (no slot). The SAME fixtures then drive the checker tests (a hand-drawn conforming diagram passes, each single-rule violation fails with the right code and line) and the layout tests (live records with `phase`/`startedAt` land in the right lane/slot).
- **Karpathy (and the parser question):** the regex skeleton is a heuristic and I keep it. A real AST would need `typescript` (~10 MB, currently a devDependency) or `acorn` at runtime, a fourth runtime dependency for a check whose grammar the guide teaches anyway. Instead the *contract* is narrowed to what the scanner can decide, and the rest is refused with a message a cold model can act on — ADR-029 did exactly this for labels and the v24 cold-model probe passed first try. The alt-group detection reuses `matchDelimiter`; it is the one new piece of scanning and it is bounded by the two syntactic forms the working notes name.

### ADR summary
- **ADR-037 — `budget` is an object `{usd?, tokens?}`; a bare number is refused; a persisted legacy number means tokens.** Context: REQ-127 changes the unit of an existing numeric field from tokens to USD. Options: (a) keep `budget: number`, redefine as USD, document (REQ literal); (b) rename to `budgetUsd`; (c) an object with both optional limits, at least one required. Decision: (c). (a) is a silent semantic change on a safety control — a v25 client or a cold model that learned "budget: 200000" keeps sending it and gets a $200k limit; (b) fixes that but leaves the owner's own default deployment (ollama, price 0) with no stopping power it had in v25; (c) does both in one shape and gives an in-flight pre-v26 run a lossless rehydration (`number → {tokens}`). Cost: `budget.total/spent()/remaining()` in-script stay numbers (USD) and gain `tokens()`; every caller changes once. Stated so the design gate does not discover it: under a tokens-ONLY budget the in-script `total` is `null` and `remaining()` is `Infinity` (no USD cap exists) while the real cap is visible only at `budget.tokens().limit` — the guide's budget section must say which accessor answers which limit, and a script that branches on `remaining()` should read `tokens()` too. **Deviation from REQ-127's literal `run_start.budget … 單位是 USD` and its option (i)/(ii) question — needs a ruling; fallback is (a) plus a guide sentence for (i).**
- **ADR-038 — pricing is pinned at admission; a run with a USD limit whose reachable model set contains an unpriced model is refused at the door (`PRICE_UNKNOWN`); without a USD limit, `costUSD:null` and `unpricedCalls` count.** Context: the reachable models are static at `run_start` (ADR-029 + REQ-091, run-manager.ts:498). Options: (a) REQ literal — always admit, `null` + count; (b) refuse mid-run at first unpriced dispatch (`refused` record like `BUDGET_EXCEEDED`); (c) refuse at admission. Decision: (c) when `budget.usd` is set, (a) otherwise. A spend limit the engine knows it cannot enforce must not be accepted silently — the v25 ruling's own words ("引擎守不住的保證不該假裝守得住") cut both ways; refusing at the door is testable, spends nothing, and names the fix (`budget.tokens`, or wait for the catalog). Consequence stated honestly: an OpenRouter listing outage refuses NEW budgeted OpenRouter runs (visible code) while unbudgeted and anthropic/ollama runs proceed. **Deviation from REQ-127's `查不到價格 → costUSD:null 且 … 計數` for the budgeted case — needs a ruling; fallback is (a) everywhere.**
- **ADR-039 — the skeleton stays a regex scan; the v2 diagram contract is narrowed to what it can decide, and undecidable constructs are refused at registration with a line-pointed message.** Extends ADR-029. Decided against a runtime `typescript`/`acorn` dependency; the alt-group detection for ternary and if/else reuses `matchDelimiter`; `switch`, loops around `agent()`, and helper-called `agent()` are refused or already `SCAN_VIOLATION`. The cold-model probe is the arbiter of whether the narrowing is teachable.
- **ADR-040 — provider errors are classified by the SDK's closed `SDKAssistantMessageError` union with a status fallback, not by the status set `{401,403,404}` alone.** The union is total (`tsc`-checked) and testable; `invalid_request` also ends the old thinking-400 four-minute retry class (Gate 7.5 round 3's defect) that a status set of three would leave open. **An extension of REQ-122's literal set — flagged; the REQ's set is the fallback.** Also makes explicit what REQ-122 implies but does not state: the fast terminal MUST abort the CLI subprocess, else "terminal in 1 s" leaves a subprocess retrying for four minutes; and that `detail` on the failed record is a NEW persisted string — redacted, then capped at 1024 bytes, swept by `redact-sweep.test.ts`.
- **ADR-041 — per-provider tool curation (commit 0f79f04, 2026-07-12) is retired.** Context recorded for the ledger, as REQ-123 requires: the original decision excluded `Read` for every non-Anthropic provider because gpt-4.1 via LiteLLM's Responses translation filled every optional field (`pages:""`) and failed ~2/3; today's retest (working notes #66) reproduced it 5/5. Decision (owner, 2026-09-08): do not support gpt-4.1 rather than keep a patch that silently changed every non-Anthropic agent's tool surface and was documented nowhere but a commit message. Consequence: the ollama default path now holds `Read`; Gate 7.5 must show it working there.
- **ADR-042 — boot refusal for retired providers is fail-closed, AND the updater runs `--check-config` before restarting.** Reconciles REQ-123 (fail-closed) with REQ-070 (never leave the service down): a stale config becomes a failed update on the old version, recorded in the result file, not an outage. When the updater's env lacks `RWE_CONFIG_PATH`, the step is skipped and recorded — never a false pass.
- **ADR-043 — `diagram_contract` is an explicit column on the immutable version row, not derived from `createdAt`.** A contract that depends on the deploy clock is not a contract; a `NULL` reads as `'v1'`, every v26 write is `'v2'`.
- **ADR-044 — the run DAG stays client-constructed DOM (`createElementNS` + `textContent`); only the box math moves server-side.** Testability wanted a server SVG string (trivially assertable); security keeps the construction path that cannot mis-escape and preserves the click-to-detail interactivity an `<img>` would kill. The unit test asserts the box math and the page source; Playwright asserts the picture.
- **ADR-045 — one effort table.** `client.ts`'s `EFFORT_PROFILES` is the live one (both gateways import it) and is extended; `params/resolve.ts`'s `ProviderEffortProfile`/`mapEffort` and `session-options-builder.ts`'s `effortMapping` are deleted and grep-guarded. Three tables for one concept is how "effort is a documented no-op" (REQ-093) happened once already.

## Risks

- **R1 (HIGH, REQ-127) — silent unit change if `budget` stays a number.** Every existing caller and every guide example becomes wrong in the permissive direction; nothing fails, nothing is protected. Mitigation: ADR-037; if overruled, the schema `description` and guide MUST lead with the unit and Gate 7.5 must include a v25-style token-scale value to observe what happens.
- **R2 (MED, REQ-127) — the budget depends on a remote listing.** OpenRouter `/models` down at `run_start` → budgeted OpenRouter runs refused (ADR-038), or admitted unpriced (REQ literal). Mitigation: TTL + last-good in memory; a persisted last-good snapshot across restarts is a deferred hardening, named not built. Also: OpenRouter's `pricing` fields are per-token strings; a parse failure must yield `null`, never `0`.
- **R3 (MED, REQ-126) — effort→reasoning is unobservable through the SDK path.** `result.usage` carries no `reasoning_tokens`; the working-notes probe bypassed the SDK. Gate 7.5 protocol: run the managed proxy with `--detailed_debug` for the validation run and grep `reasoning_effort`; plus a low-vs-high output-token difference on `gemini-3.8-flash`. The `REASONING_BUDGET` thresholds are pinned to the deployed LiteLLM version — a LiteLLM upgrade can move them silently; the harness's `effortApplied.value` records what was SENT, which is the honest claim.
- **R4 (MED, REQ-128) — false refusals from the regex skeleton.** Constructs it cannot see are refused (ADR-039); constructs it mis-sees (an `agent(` inside a string or template literal — `matchDelimiter` is string-aware, but a regex in a comment is not) produce a wrong `ExpectedGraph` and a confusing refusal. Mitigation: the envelope carries the expected structure as data; the cold-model probe (REQ-117/128) is the acceptance and any failure is a documentation defect by the v24 ruling.
- **R5 (MED, REQ-123) — deploy ordering.** The four gpt41* rows on the production box must go before the first v26 restart; ADR-042 makes the failure a recorded non-update rather than an outage, but only if `RWE_CONFIG_PATH` is added to `update.env` — a DEPLOY.md step with no engine-side enforcement.
- **R6 (MED, REQ-123) — the ollama default path now holds `Read`.** qwen2.5:7b may misuse the Anthropic-tuned `Read` schema the way gpt-4.1 did. Owner accepted ("不支援就好"); Gate 7.5's ollama run with a real `Read` call is the evidence either way.
- **R7 (LOW, REQ-122) — abort semantics.** `Options.abortController` killing the CLI was verified for the timeout path (Gate 7.5 round 4); the same controller is reused, but the fake-session test cannot prove a real subprocess dies — Gate 7.5 must `ps` after a forced 401.
- **R8 (LOW, REQ-124) — nested frames share the phase timeline;** composite runs may show extra lanes with a warning. Recorded approximation, not hidden.
- **R9 (LOW, REQ-127) — cache rates for Anthropic are a static ratio** (0.1× / 1.25×) that Anthropic has changed before; the table carries a `reviewedAt` date like `COST_LEVEL_BANDS` does.
- **R10 (LOW, REQ-129) — zoom on an `<img>`-embedded SVG** scales crisply (vector) but the `fit` state must be recomputed on window resize; one `resize` listener.
- **R12 (MED, REQ-124) — the phase stamp is wrong under IPC batching unless taken at receipt.** Verified 5/5 with a probe: `agent` + `phase` messages in one chunk make a handler-time read see the later phase. ARCH-114 closes it structurally; the ordering test is the guard. A second cohort risk: pre-v26 journals resumed across the upgrade cannot be placed exactly (no agreeing timestamps) — fallback + warning, named in the acceptance (G14).
- **R13 (HIGH, REQ-127 scope) — every trigger-started run is outside the money cap.** Cron/once, resident and webhook fire `start()` with no `budget` (only `run_start` carries one); v26 turns the number into USD, so the cap protects attended runs and misses exactly the unattended ones a budget exists for. Not designable inside REQ-121..130's text — G12 escalates it with the shape ready if ruled in.
- **R11 (INFO) — a cheap Gate 7.5 cross-check:** the SDK's `modelUsage[model].costUSD` for anthropic-direct calls should agree with `priceCall` to the cent; log it in the validation evidence, do not add a field.

## Conflicts between my three lenses (argued, with the tie-break)

- **C1 — REQ-127, unpriced model under a USD budget.** *Security:* fail closed — refuse at admission. *Scale/consistency:* refuse at admission is also the consistent choice (spend 0, one decision point, no mid-run `refused` records that depend on dispatch order). *Testability:* neutral, both are pure. *Simplicity:* the REQ literal (always admit, `null` + count) is fewer lines. **Tie-break:** security, but ONLY where the caller asked for a USD limit — the REQ literal stands for unbudgeted runs. Flagged (ADR-038).
- **C2 — REQ-127, the shape of `budget`.** *Security:* an object (no silent unit change). *Scale/consistency:* an object (legacy number rehydrates losslessly as tokens; the ollama path keeps a working limit). *Testability:* an object (two independent limits, each a one-line test). *Simplicity:* a number, as written. **Tie-break:** the object — the three substantive lenses agree and simplicity's saving is one type. Flagged (ADR-037).
- **C3 — REQ-123 boot refusal vs REQ-070 never-down.** *Security:* fail closed at boot. *Scale/self-sustainability:* an auto-restarting updater plus fail-closed boot is an outage generator. *Testability:* both are testable; the updater already has an integration harness with a fake `SYSTEMCTL`. **Tie-break:** both, via `--check-config` in the existing `revert_and_fail` path (ADR-042) — twelve lines of shell, no new mechanism.
- **C4 — REQ-128 skeleton fidelity.** *Testability and security:* an AST is exact; a regex has false positives and negatives. *Simplicity:* no fourth runtime dependency; the sandbox already strips types with node's native transform, so `typescript` at runtime would exist for the checker alone. **Tie-break:** regex + narrowed contract + refusal of the undecidable (ADR-039), because the cold-model probe already proved the "refuse and teach" pattern works for labels.
- **C5 — REQ-129 where the SVG is built.** *Testability:* a server-side string is trivially assertable and removes ~60 lines of inline JS. *Security:* `createElementNS`+`textContent` cannot mis-escape and keeps interactivity. **Tie-break:** security; testability gets `dagBox` and a page-source assertion (ADR-044).
- **C6 — REQ-126 one writer of `thinking`.** *Consistency/testability:* one function for both wire fields. *Simplicity (minimal diff):* leave `thinkingFor` and add a branch. **Tie-break:** one writer — a minimal diff that leaves two writers of one field is the defect REQ-093 already taught this ledger about; the deletion of two dead tables makes the net diff negative anyway (ADR-045).
- **C7 — REQ-126/127 where per-model facts come from.** *Scale:* not per dispatch (fetch storms). *Consistency:* not live during a run (a mid-run price change moves the budget). *Security:* a pin the caller cannot influence after admission. **Tie-break:** pin at admission from a TTL'd book (ARCH-116) — the freshest price at dispatch is the one property nobody asked for.
- **C8 — REQ-122 classification key.** *Simplicity:* the REQ's status set. *Testability:* the SDK's closed union is `tsc`-total. *Self-sustainability:* the union also closes `invalid_request` (the thinking-400 class) which the set does not. **Tie-break:** the union with a status fallback (ADR-040), flagged as an extension.
- **C9 — REQ-121 where "required" lives.** *Consumability:* the schema should say `contentB64` is required. *Testability/REQ:* a specific code with a pointer. **Tie-break:** the post-schema validator with the specific code (existing precedent), the schema description stating "REQUIRED" in words so `tools/list` does not lie.
- **C10 — REQ-122, how much of the SDK's unmapped traffic to keep.** *Testability/observability:* capture every unmapped `system` message as a typed event so the next silent drop is a visible row. *Security:* provider response bodies are the one stream the engine does not author; storing more of them widens the exfiltration surface REQ-083 closes, and redaction is value-exact (it cannot catch a credential it was not told about). *Simplicity:* handle `api_retry` and nothing else. **Tie-break:** security, with testability's irreducible part kept — the subtype NAME and a COUNT (`meta.unmappedMessages`), never the payload; ~6 lines.
